## 2. 检索与代码表示

### Q1：一次问答到底经过什么？

固定Git提交→结构切分与索引→召回候选→排序/重排→原文窗口选择→生成。普通RAG取一次初始原文后作答；Agent共享初始取证组件，再由SDK根据观察补查，最后输出答案和引用。

索引单元、实际交付的原文窗口和模型当前可见原文是三个对象。缓存有某个类，既不等于选源器交付了该类，也不等于它仍在后续模型输入中。代码入口：[chunking.py](../src/repomentor/chunking.py)→[retrieval_factory.py](../src/repomentor/retrieval_factory.py)→[shared_sources.py](../src/repomentor/shared_sources.py)。

### Q2：为什么按结构切？块大小和TopK怎样确定？

函数、类、控制流和测试断言有结构边界，固定字符截断容易损坏声明与局部关系。Tree-sitter提供语法范围，解析不适用时有行级回退；Python另用AST提供有限静态关系。长结构仍受预算约束，结构切分不保证整类或全部依赖都进入输入。

当前默认块上界768，初始候选20、最多6个单元、原文8,000字节；这里块与源码装配按UTF-8字节计数，不能说“768个Qwen token”。这些是工程预算，并未做系统超参搜索。若被问为何不是别的值，说明当前窗口与运行约束，承认未证明最优；不要编造TopK曲线。

### Q3：手写BM25，解释每一项

```text
IDF(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
score(q,d) = Σ IDF(t) × tf(t,d)(k1+1)
                     / [tf(t,d) + k1(1-b+b|d|/avgdl)]
k1 = 1.5，b = 0.75
```

`N`是块数，`df`是含词块数，`tf`是块内词频。`k1`控制词频饱和，`b`控制长度归一化；`b=0`时消去长度项。词频增大不会使分数无限线性增长，同样词频下长块受到更强归一化。

当前[实现](../src/repomentor/retrieval.py)保留标识符并拆分camelCase、下划线和路径，中文使用二元组及少量查询扩展；块词频包含正文和双倍路径词。按不同查询词累加，不额外引入查询词频项。路径过滤在候选排名与截断之前发生，IDF和平均长度仍基于全索引。应能用两段长短源码解释分数变化，而不只背公式。

### Q4：向量怎样来？FAISS是不是数据库？

[NeuralRetrieval](../src/repomentor/neural_retrieval.py)用固定权重的Qwen3-Embedding-0.6B，查询加任务指令，文档为路径与正文；采用最后有效token表示及L2归一化，得到1024维向量。采用作者的[查询指令与池化方式](https://github.com/QwenLM/Qwen3-Embedding/blob/main/README.md)，项目没有训练该模型。

向量矩阵与输入推理结果有本地缓存，检索索引为[FAISS IndexFlatIP](../src/repomentor/hybrid_retrieval.py)，做精确内积搜索。两端向量归一化后内积等于余弦相似度，可由`cos(x,y)=x·y/(||x||||y||)`推导；[FAISS作者说明](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)给出相同条件。项目没有使用HNSW、IVF、Milvus或Chroma；SQLite存运行与记账状态，不是向量检索层。

选择FlatIP是当前仓库规模下的简单实现，没有大规模吞吐或不同索引的质量/时延实测，不能声称它在所有规模下最佳。

### Q5：为什么双路召回？RRF怎样算？

词法检索擅长精确符号与路径，向量检索提供语义候选；互补性是设计动机，是否有效看当前任务结果。两路原始分数量纲不同，不能直接等权相加。当前[融合实现](../src/repomentor/hybrid_retrieval.py)为：

```text
RRF(d) = Σ 1 / (60 + rank_i(d))
```

名次从1开始，每一路先去重，未出现的候选不贡献该路分数。例如两路均第2名得到`2/62`，只在一路第1名得到`1/61`。常数降低单路极高名次的支配程度，60采用[原论文](https://cormack.uwaterloo.ca/cormack/cormacksigir09-rrf.pdf)的常用设置，项目没有证明它是本数据最优值。

### Q6：重排与embedding检索有什么不同？

embedding分别编码查询和块，库向量可离线缓存；重排把查询和候选正文联合输入模型，在较小候选集上细判相关性，因此不能凭重排恢复根本没召回的证据。

当前Qwen3-Reranker-0.6B按照[作者的yes/no协议](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)读取下一token两个logit：`score=exp(z_yes)/(exp(z_yes)+exp(z_no))`，实现使用稳定softmax。它是联合输入的相关性分数，不是生成一段长解释后再打分，也不能当成已校准的答案正确概率。代码见[rerank](../src/repomentor/neural_retrieval.py)。

### Q7：代码增强是什么？为何没有提高？

[CodeRetrievalIndex](../src/repomentor/code_retrieval.py)增加明确路径、符号、一跳静态callee与实现/测试角色候选，还复用现有搜索补特定测试和可靠导入绑定。它是代码定位与选源启发式，不是完整运行时调用图，不保证动态分派、反射或同名成员都能正确解析。

50题中代码增强63.36低于普通BM25的64.46，新增30题同样略低。Streamlink-027暴露通用问题仍触发实现角色优先，Pytest-017则是原文充分仍误读。可以解释局部机制有帮助、总体收益未得到支持，不能把一两个修复案例替换成普遍提升；也不能从单次顺序差异推出唯一因果。

## 3. Agent与运行环境

### Q8：Agent自主在哪里？与workflow区别是什么？

模型决定下一次调用哪个工具、传什么查询以及何时作答；SDK的`Runner.run`执行循环。应用提供六个只读工具：`navigate_symbol`、`search_code`、`search_docs`、`read_code`、`find_tests`、`trace_dependencies`；`submit_answer`另属答案提交，不计仓库操作。

学习报告的角色顺序由代码预定，属于固定工作流；普通问答默认单Agent。这个区分与[Anthropic对workflow和agent的说明](https://www.anthropic.com/research/building-effective-agents)一致。当前没有证据要求增加多Agent或MCP层，工具数量也不是自主性和效果指标。

### Q9：哪些是SDK做的，哪些是自己的？

SDK负责模型与工具迭代、生命周期；项目负责工具契约、只读快照、候选/原文交付、预算、上下文过滤、可见来源与终态校验、记录及恢复。循环复用SDK，应用约束由[sdk_agent.py](../src/repomentor/sdk_agent.py)、[sdk_context.py](../src/repomentor/sdk_context.py)、[agent_tools.py](../src/repomentor/agent_tools.py)等实现。仓库内同名`harness.py`主要服务旧报告流程，不代表所有Agent约束集中在那里。

评测框架另管冻结任务、调用正常引擎、保存原始结果、导入评分和聚合成本。运行环境与评测环境应能分清；工程测试通过不意味着回答正确。

### Q10：上下文怎样控制？

| 预算 | 实际意义 |
| --- | --- |
| 6单元 / 8,000字节 | 初始源码预算；一个单元可能对应多个原文窗口 |
| 36,000字节 | SDK累计交付源码预算，区别于当前输入窗口 |
| 16,384 tokens | 完整模型请求窗口，包含指令、历史、工具/schema及输出预留 |
| 产品默认8次决策、6次仓库操作、300秒 | 普通问答预算 |
| 本次评测6次决策、6次仓库操作、360秒 | 为评测显式冻结的预算；研究输出1536，最终输出2048 tokens |

完整约束为`T(指令+历史+工具+schema+原文)+输出预留+余量≤窗口`。上下文过滤需保持工具调用/返回对协议完整，记录实际保留的原文；传输边界再检查请求。旧助手总结和导航位置不等于源码，裁掉的原文不能继续作为当前引用依据。

设计采用初始预取与按需取证，和[Anthropic的上下文工程讨论](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)有相通处；这里“混合取证策略”与“BM25+向量混合检索”是不同维度。

### Q11：为什么同批read和submit仍可能非法？

记已存档原文为`H_t`，当前实际输入原文为`V_t`。裁剪后`V_t`可以只是`H_t`的一部分。同一模型输出生成`read_code(L3)`和`submit_answer(引用L3)`时，两个参数均基于旧的`V_t`，即使工具按顺序执行也不能倒填见过的证据。

项目冻结该次模型调用前的`V_t`校验提交。本轮引用越界就返回错误；L3进入下一次模型输入后再允许引用。这个拒绝和继续提交路径由[真实SDK Runner离线测试](../tests/test_sdk_agent.py)覆盖，模型为可控脚本；不能说本地Qwen已展示线上恢复成功。

来源校验检查快照身份、原文和行范围，不证明自然语言蕴含。模型引用正确行号仍可能读反分支；该边界在Flask-048中很具体。

### Q12：Agent空转、恢复和重复请求怎样处理？

仓库操作、模型请求和墙钟时间分别限额；已读或重复动作返回结构化错误，不能无限刷工具。50题Agent的176次仓库操作中，31次already_read、9次duplicate_action，占22.7%；保护生效但仍浪费决策，不能通过放宽重复读取来包装效果。

模型配置、快照、排除范围、工具/提示和索引身份参与缓存与会话校验。完成请求可按request ID回放；检查点保存失败位置和状态，显式恢复复用已有工具结果。自动HTTP重试关闭，不确定是否发出的请求也记账；恢复不保证远端恰好执行一次。

目标仓库仅作为只读材料，不执行其指令；路径、大小与排除范围受控，源码内的指令当作数据。当前未做完备提示注入攻防验证，不能声称系统已经安全认证。

## 4. 评测必须说清的事

### Q13：五组区别是什么？闭卷里有源码吗？

| 条件 | 给生成器什么 | 能否继续读仓库 |
| --- | --- | --- |
| 闭卷 | 题干、仓库名、允许已有知识的规则；没有源码和参考答案 | 否 |
| 普通BM25 RAG | BM25召回的结构块，经共享打包器交付 | 否 |
| 代码增强BM25 RAG | 同一基础切分，加代码定位和排序启发式 | 否 |
| 混合重排RAG | BM25、向量、RRF、重排后的初始原文 | 否 |
| SDK Agentic RAG | 与同题混合组完全相同的初始原文，再按观察补查 | 是 |

生成器均为本地Qwen3.5-9B Q4_K_M，16K窗口，temperature=0、seed=42、关闭思考；这减少配置差异，仍不能由单次运行断言确定性或稳定增益。Agent的提示、导航和多轮预算也不同，因此是完整流程比较，不是纯工具或纯某个检索模块的因果消融。

### Q14：如何参照SWE-QA官方评测？

[作者仓库](https://github.com/peng-weihan/SWE-QA-Bench)把问答与固定commit绑定，并提供下载目标仓库和运行方法。当前下载对应仓库的固定源码，不安装或运行目标项目；复用自己的检索与SDK引擎，使用官方五维量表。生成模型、检索权重和评审方式均不同于论文，不能称完整复现其结果。

全数据有720题、15库，当前只取Flask、Requests、Pytest、Streamlink共50题。旧20题用于开发，新30题生成前按固定种子选定，排除本地题库和旧样本的规范化同文题；没有语义去重或预训练污染保证，也没有跨新仓库验证。旧100份答案与评分原样复用，新150份不挑最好尝试。

### Q15：77.96是什么？评分可靠吗？

### Q16：哪些可信度检查已经做，哪些没有？

已做：同题五组、固定生成配置、实际请求与原始答案留存、四库分层报告、来源字节与哈希核验、成本与退步保留。425次实际请求和2777处源码窗口通过核验；闭卷无源码、Agent与混合初始证据一致。这些是输入与记录检查，不是语义正确证明。

生成前标记4道主要参考问题，保留50题主结果，再给排除这4题的46题敏感性结果，五组排序不变。例如Requests-035无chardet时直接返回utf-8，不能照参考混成读取content的路径。参考也需要源码复核。

未做：全720题、新仓库泛化、多seed稳定性、独立人工标注、等推理成本对照，以及全库长上下文/更强模型对照。四仓库聚类bootstrap中Agent减混合区间约[3.36,11.52]，仅四个聚类，不据此宣称稳定泛化或显著性。50题已曝光，后续不放入训练或再称未见测试。

### Q17：Agent更好吗，值得成本吗？

样本均分Agent相对BM25高13.50分，相对混合高7.44分；后一个对照26题改善、8题持平、16题退步。平均生成请求4.5对1，观察到的平均耗时约68.75对14.82秒，使用热索引且有GPU模型换入换出，不是冷启动或生产吞吐，也没有把调用倍数换算成金额。

可以判断复杂查证有进一步取证的价值；当前未实现并验证自动路由何时值得用Agent，不能宣称已经节约成本。更简单的流程仍是必要基线，负结果也保留。只讲分数提升而不讲代价，会使结果难以评估。

### Q18：怎样从bad case决定改哪里？

| 先问的问题 | 当前证据 | 能推出什么 |
| --- | --- | --- |
| 索引中有目标吗，实际召回/搜索到吗？ | Streamlink-019目标类在原索引，但五组请求均没送入声明 | 目标召回与搜索转向不足，不能说代码不存在 |
| 决定性源码进入了实际请求吗？ | Flask-042两种BM25漏类归属，混合交付完整类段 | 查选源边界和预算；该例不是Agent工具收益 |
| 原文充分时模型是否读对？ | Pytest-017同六段原文仍自相矛盾，Flask-048忽略return | 查条件理解、证据利用与停止判断；堆导航未必有效 |
| 原始模型输出是不是本来就不完整？ | 两份合法JSON正文提前结束，stop且远低于token上限 | 保留生成失败；不能凭观感归咎客户端截断 |

案例是事后挑选的诊断，不是穷尽错误分类统计。本轮50题没有完整gold来源标注下的Recall@K/NDCG总表，不能编造召回率提升；历史P6.3检索指标属于另一题集，单例来源覆盖也不等于全体召回率。原件：[失败分析](../experiments/sweqa-50-2026-11-03/failure-analysis.json)。

这种分别检查过程、结果和成本的准备方法，也可参考[Anthropic的Agent评测讨论](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。本项目主要输出解释，使用量表与源码复核；不能套用“代码执行测试通过”作为自己的答案验收方式。
